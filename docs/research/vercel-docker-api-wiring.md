# Research: Wiring Vercel web to the Docker API (#10)

Date: 2026-11-16 · Ticket: [#10](https://github.com/SiddharthMuramkar/foa-platform/issues/10) · Map: [#2](https://github.com/SiddharthMuramkar/foa-platform/issues/2) · SPEC §3.3–§3.7, §4.1 SG-01/SG-05, §8.1, NFR-01–06/09/11

## Answer

- The SPEC §3.3–§3.4 shape works on Vercel + a VPS. It needs: the API on `api.foaglobal.org` behind a TLS reverse proxy; an exact-origin CORS list; a small `azp` check instead of Clerk `authorizedParties`; a secret-guarded `POST /api/revalidate` that purges through `@vercel/functions` (so a dropped purge is detected); and raw-body webhook routes that store each event and enqueue its job in one transaction.
- **Do not pass `authorizedParties` to `clerkMiddleware`, in any environment.** Clerk mints cookie session tokens without `azp` on top-level navigations, and `@clerk/backend` ≥ 3.11.1 rejects every azp-less token once `authorizedParties` is set. SSR forwards those cookie tokens (§3.3), so production would return 401 on part of SSR traffic. Instead, use Clerk's manual-verification rule: reject a token whose `azp` is present and not allowed, and accept a token with no `azp`.
- SG-05 (takedown within 5 minutes) needs more than `revalidateTag`. The API must `await` a **delete** purge by tag **and by source image** during the request. `next/image` keeps optimised copies for ≥ 4 h, and a tag purge does not touch them. A queued job is only the fallback.
- **Previews** cannot use Clerk production keys on `*.vercel.app`. They use the Clerk development instance, Razorpay test mode and Turnstile test keys against a non-production API. That API is capped at 100 users. Which API that is, before and after the VPS exists, is #7's call; options are below.
- **Vercel Pro is the baseline**: FOA collects Enrolment fees and auction payments, which Hobby forbids. Set the function region to **`bom1` (Mumbai)**, put the VPS in Mumbai, and cache public reads in Vercel. The 5 s auction poll (1,000 viewers ≈ 200 req/s) needs its own cheap endpoint and its own rate-limit bucket.

## Findings

### 1. Domain, TLS, CORS

- **Domain/TLS.** Point an A/AAAA record for `api.foaglobal.org` at the VPS. Caddy gives automatic HTTPS. Its `reverse_proxy` sets `X-Forwarded-For/Proto/Host` and by default ignores client-supplied values. HSTS (NFR-05) is one `header` line ([Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy), [Caddy header](https://caddyserver.com/docs/caddyfile/directives/header)). Razorpay delivers webhooks only to ports 80/443 and keeps separate Live and Test webhook URLs ([Razorpay webhooks](https://razorpay.com/docs/webhooks)). Host hardening belongs to #11.
- **Express behind the proxy.** Default to `app.set('trust proxy', 1)`, because Caddy is the only hop. Trusting the Docker network's subnet also works. Do **not** use `'loopback'`: it trusts only `127.0.0.1/8` and `::1`, and an API container sees the proxy as a Docker bridge IP. `req.ip` would then be the proxy's IP, and every client would share one §8.1 rate-limit bucket. `'loopback'` fits only when the proxy and API both run on the host network ([Express behind proxies](https://expressjs.com/en/guide/behind-proxies.html)).
- **Why a Bearer header is needed.** Clerk's `__session` cookie is scoped to the app domain and never shared with subdomains. For `foaglobal.org` → `api.foaglobal.org`, Clerk says to send the token in `Authorization`, which matches §3.3 ([Clerk: how Clerk works](https://github.com/clerk/clerk-docs/blob/main/docs/guides/how-clerk-works/overview.mdx), [making requests](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/making-requests.mdx)).
- **Preview URLs are dynamic.** Commit URLs look like `<project>-<hash>-<scope-slug>.vercel.app` and branch URLs like `<project>-git-<branch>-<scope-slug>.vercel.app`. Labels over 63 characters are truncated, and anti-phishing rules can shorten them further. On Pro, a **Preview Deployment Suffix** replaces `vercel.app` with a custom domain ([Vercel generated URLs](https://vercel.com/docs/deployments/generated-urls), updated 2026-09-08).
- **Clerk and previews.** Clerk production keys do not work on the host's preview domain, so previews use **development** keys ([Clerk: managing environments](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/managing-environments.mdx), [Clerk on Vercel](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/deployment/vercel.mdx)). Each instance signs with its own JWT key, so preview and production traffic cannot share one API instance. Development instances are **capped at 100 users**, user data cannot be moved to production, and Clerk delivers at most 100 emails and 20 SMS a month plus a daily recipient limit per workspace ([managing environments](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/managing-environments.mdx), [test emails and phones](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/testing/test-emails-and-phones.mdx)).
- **The `cors` package.** `origin` accepts an array of strings and RegExps. On a match it reflects the request origin and sets `Vary: Origin`. It also takes `allowedHeaders`, `exposedHeaders`, `credentials` and `maxAge` ([expressjs/cors](https://github.com/expressjs/cors/blob/master/_autodocs/configuration.md)).
- **Preflight caching.** Browsers cap `Access-Control-Max-Age`: Chromium 76+ at 7200 s, Firefox at 86400 s, and **WebKit at 600 s**. Every browser on iOS uses WebKit (NFR-11 lists Safari iOS ≥ 16), so on iPhones signed-in calls re-preflight every 10 minutes. The default is 5 s ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Max-Age), [WebKit CrossOriginPreflightResultCache.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/loader/CrossOriginPreflightResultCache.cpp)). The preflight cache is keyed per URL. Any request carrying `Authorization`, `Idempotency-Key` or tracing headers is preflighted. A plain public GET with no custom headers is not.
- **Tracing headers (NFR-09).** Once `tracePropagationTargets` includes `api.foaglobal.org`, Sentry browser tracing adds `sentry-trace` and `baggage` (and `traceparent` if `propagateTraceparent` is on). Preflights fail unless those headers are allowed ([Sentry: dealing with CORS](https://docs.sentry.io/platforms/javascript/tracing/distributed-tracing/dealing-with-cors-issues/)). Leave the auction-poll URL out of `tracePropagationTargets` so the poll stays a simple, unpreflighted request.
- **Readable response headers.** JS on another origin can read only the CORS-safelisted response headers. `Date` and `Retry-After` are not on that list ([MDN safelisted response headers](https://developer.mozilla.org/en-US/docs/Glossary/CORS-safelisted_response_header)). Countdowns already have a source: §8.2's `GET /auctions/:id` returns `serverTime` in the body. Expose `Retry-After` so the client can back off after a 429 `RATE_LIMITED`.
- **Request id.** Browsers do not send `X-Request-Id`, because it would preflight the poll. The API generates the id and returns it. SSR forwards Vercel's `x-vercel-id` as `X-Request-Id`; this is server to server, so CORS does not apply.
- **Proposed config.**
  - Production: `origin` = `CORS_ORIGINS` (exact: `https://foaglobal.org`, `https://www.foaglobal.org`).
  - Non-production: `CORS_ORIGINS` plus `CORS_ORIGIN_PATTERN`, e.g. `/^https:\/\/<project>-(git-[a-z0-9-]+|[a-z0-9]+)-<scope>\.vercel\.app$/`. With a Preview Deployment Suffix, anchor the pattern on the FOA-owned suffix domain instead.
  - Both: `credentials: false` (Bearer only, no cookies) · `allowedHeaders: Authorization, Content-Type, Idempotency-Key, sentry-trace, baggage` (+ `traceparent` if enabled) · `exposedHeaders: X-Request-Id, Retry-After` · `maxAge: 7200`.
- **Other origin-bound pieces.** (a) Turnstile widgets render only on hostnames registered for the sitekey, so they fail on `*.vercel.app`. Use Cloudflare's dummy test sitekey and secret in preview and non-production environments; they work on any domain ([Turnstile testing](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)). (b) Browser presigned PUTs go straight to the bucket (§3.5), so the **bucket's** CORS must list the web origins. The prod bucket gets exact origins. The preview bucket gets `https://<project>-*-<scope>.vercel.app`, since R2 allows at most one `*` per origin pattern ([R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/)). If #7 replaces R2, the same rule applies to the S3-compatible container.

### 2. Auth (Clerk ↔ Express)

- **Getting the token.** In the browser, `useAuth().getToken()` returns a token to send as `Authorization: Bearer`. On the server, `(await auth()).getToken()` does the same; this is the token from the request's session cookie ([Clerk useAuth](https://github.com/clerk/clerk-docs/blob/main/clerk-typedoc/react/use-auth.mdx)). Session tokens expire after **60 s**, so fetch one per request and never store one in a `'use cache'` scope ([Clerk session token](https://github.com/clerk/clerk-docs/blob/main/docs/guides/how-clerk-works/overview.mdx)).
- **Verifying without a network call.** Use `clerkMiddleware({ jwtKey })` with `jwtKey` = the PEM public key, or set `CLERK_JWT_KEY`. Without it, `verifyToken` fetches the JWKS from Clerk's Backend API ([clerkMiddleware options](https://github.com/clerk/clerk-docs/blob/main/docs/_partials/clerk-middleware-options.mdx), [verifyToken](https://github.com/clerk/clerk-docs/blob/main/clerk-typedoc/backend/verify-token.mdx)). Just-in-time `User` creation (§3.4) still calls `clerkClient.users.getUser` once per new user, so `CLERK_SECRET_KEY` stays. The SDK convention also expects `CLERK_PUBLISHABLE_KEY` on the backend ([Clerk SDK env conventions](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/sdk-development/conventions.mdx)).
- **`azp` is not always present.** Clerk's reference says `azp` is the `Origin` of the Frontend API request and "could be omitted if … `Origin` is empty or null" ([session tokens](https://github.com/clerk/clerk-docs/blob/main/docs/guides/sessions/session-tokens.mdx)). In practice the Frontend API mints cookie `__session` tokens **without `azp`** on top-level navigations. [clerk/javascript#8231](https://github.com/clerk/javascript/issues/8231) (open) reports this on Next.js 16.2 + `@clerk/nextjs` v7 on Vercel at about 2,000 tokens a day. [#9249](https://github.com/clerk/javascript/issues/9249) was closed as not_planned, and a 2026-11-11 comment there reports it still live in `@clerk/backend` 3.27.0.
- **`authorizedParties` rejects azp-less tokens.** Since `@clerk/backend` 3.11.1 (PR [#8877](https://github.com/clerk/javascript/issues/8877), 2026-07-07), `assertAuthorizedPartiesClaim` throws on a missing `azp` whenever `authorizedParties` is set, including for header-carried tokens. This is still true on `main` (3.29.0) ([assertions.ts](https://github.com/clerk/javascript/blob/main/packages/backend/src/jwt/assertions.ts)). SSR forwards cookie-derived tokens, so `authorizedParties` would cause 401s in production.
- **Rule to use.** Do not pass `authorizedParties`. After `clerkMiddleware`, add one small middleware for every environment: if `getAuth(req).sessionClaims.azp` is present and is not in `CORS_ORIGINS` (or does not match `CORS_ORIGIN_PATTERN` outside production), return 401; if `azp` is absent, accept. This is Clerk's manual-verification rule: "If the `azp` claim doesn't exist, you can skip this step" ([manual JWT verification](https://github.com/clerk/clerk-docs/blob/main/docs/guides/sessions/manual-jwt-verification.mdx)). It may be tightened to "azp-less only with a valid `API_SERVER_KEY`" once the S0 token test (Open risks) shows browser tokens always carry `azp`.
- **Clerk webhooks.** Use `verifyWebhook(req)` from `@clerk/express/webhooks` behind `express.raw({ type: 'application/json' })`, reading `CLERK_WEBHOOK_SIGNING_SECRET` ([Clerk syncing](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/webhooks/syncing.mdx), [overview](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/webhooks/overview.mdx)). Svix delivers them on its retry schedule (§5). The development instance sends to the non-production API and the production instance to the production API, each with its own secret.
- **Dev-instance quota.** CI (§11 Playwright), local development (§3.7) and phone-checked previews all draw on the same 100-user dev instance. Use `+clerk_test` addresses (test OTP `424242`, no email sent), Testing Tokens and reused seeded users for CI and demos ([Playwright testing](https://github.com/clerk/clerk-docs/blob/main/docs/guides/development/testing/playwright/test-authenticated-flows.mdx)). If that is not enough, give previews and staging their own Clerk application, separate from local development.

### 3. Revalidation

- **Which call to use.** `updateTag` **throws outside Server Actions**, so a route handler uses `revalidateTag(tag, 'max')` or `revalidateTag(tag, { expire: 0 })` ([Next 16.2 revalidateTag](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/03-api-reference/04-functions/revalidateTag.mdx), [updateTag](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/03-api-reference/04-functions/updateTag.mdx)). `revalidateTag` takes **one tag per call**.
- **What a purge does on Vercel** ([Vercel purge](https://vercel.com/docs/caching/cdn-cache/purge), updated 2026-09-03).
  - A tag purge clears the CDN cache, Runtime Cache and Data Cache.
  - Invalidate (serve stale, refresh in background): `revalidateTag(tag,'max')`, or `invalidateByTag()` from `@vercel/functions`. Delete (refetch in the foreground): `revalidateTag(tag)` (deprecated single-argument form), `revalidatePath`, `updateTag`, or `dangerouslyDeleteByTag()`.
  - `{ expire: 0 }` is **not** in Vercel's table. Next 16.4.5 says the deprecated single-argument form "behaves like `{ expire: 0 }`", so it is probably a delete, but no Vercel source says so ([Next 16.4.5 revalidateTag](https://github.com/vercel/next.js/blob/v16.4.5/docs/01-app/03-api-reference/04-functions/revalidateTag.mdx)).
  - **Rate limit**: 200 purge calls/s per team on Pro, averaged over 30 s. The limit **counts calls, not tags**. `invalidateByTag()`/`dangerouslyDeleteByTag()` take `string | string[]` and **throw an error containing `429`** when limited. `next/cache` functions do not throw; they only log a warning.
  - **Tags are scoped to project + environment.** `@vercel/functions` purges the environment of the deployment that runs it. The REST API takes an optional `target` (preview/production; the default is all environments), takes up to 16 tags per call, and is rate-limited under the REST limits.
- **Images (SG-05).** A tag purge does not touch Vercel's image-optimisation cache. `next/image` keeps optimised copies for `minimumCacheTTL` (default **14400 s = 4 h**) or the upstream `Cache-Control` max-age, whichever is larger ([Next 16.2 Image](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/03-api-reference/02-components/image.mdx)). Vercel tags each optimised image with its source URL, and you purge those with `invalidateBySrcImage()` / `dangerouslyDeleteBySrcImage()` (`string | string[]`, which must match the `src` exactly) or REST `POST /v1/edge-cache/dangerously-delete-by-src-images` ([@vercel/functions](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package), [REST invalidate by source image](https://vercel.com/docs/rest-api/edge-cache/invalidate-by-source-image)). Without this, a withdrawn minor's artwork stays at `/_next/image` for hours after `foa-public` is cleaned.
- **Preview protection.** Standard Deployment Protection covers preview and generated URLs but not the production custom domain. A caller that targets a preview URL must send `x-vercel-protection-bypass` ([Vercel protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication), [bypass for automation](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)). No stable preview URL exists, because previews are per PR and `main` deploys to production. So the non-production API should call the **REST** purge endpoints with `target=preview` instead. That needs a Vercel access token but no URL and no bypass secret. The alternative is the branch URL of a long-lived `staging` branch plus the bypass header.

### 4. Latency and load (India; NFR-01/02/03)

- **Regions.** Vercel functions run in `iad1` (Washington DC) by default. Set `vercel.json` `"regions": ["bom1"]` (Mumbai, AWS `ap-south-1`). Vercel advises putting functions near their data source ([function regions](https://vercel.com/docs/functions/configuring-functions/region), [regions list](https://vercel.com/docs/regions), both updated 2026-08-11). With the default, every sequential server fetch makes a US↔India round trip, and the first one on a connection also pays for TLS. That uses up the LCP < 2.5 s budget fast.
- **Plan.** Hobby is for non-commercial personal use only. "Any method of requesting or processing payment from visitors" counts as commercial; donations alone are exempt ([fair use](https://vercel.com/docs/limits/fair-use-guidelines)). FOA takes Enrolment fees and auction payments (§3.6), so production needs **Pro**. Pro also unlocks a Preview Deployment Suffix and multi-region.
- **Keep-alive.** Node 24's `fetch` (undici) keeps sockets alive by default: a 4 s idle timeout, which server `Keep-Alive` hints can raise to 600 s, and 100 cached TLS sessions ([undici Client](https://github.com/nodejs/undici/blob/main/docs/docs/api/Client.md)). Next configures keep-alive itself only on Node < 18 ([httpAgentOptions](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/03-api-reference/05-config/01-next-config-js/httpAgentOptions.mdx)). Fluid compute reuses warm instances, and with them warm sockets ([Fluid compute](https://vercel.com/docs/fluid-compute)). Measure before tuning.
- **Caching.** Plain `'use cache'` is **in-memory per instance**. `'use cache: remote'` is Runtime Cache on Vercel and can be purged by tag ([Next caching](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/01-getting-started/08-caching.mdx), [use cache: remote](https://github.com/vercel/next.js/blob/v16.2.9/docs/01-app/03-api-reference/01-directives/use-cache-remote.mdx)).
  - Public data in the static shell: `'use cache'` + `cacheTag`. This is **prerendered during `next build`**, so every production and preview build calls the API, and a build fails when the API is unreachable. Either put public data behind `<Suspense>` with a fallback so it renders at request time, or catch API errors during the build. Build traffic goes in its own rate-limit bucket.
  - Public data under dynamic boundaries: `'use cache: remote'` + `cacheTag`.
  - Signed-in reads: never cached.
- **Browser → API.** Browser calls go straight to the VPS, so a VPS in India is what keeps NFR-02's p95 meaningful. Preflights add one round trip per URL per cache window: 2 h on Chromium, **10 min on iOS** (§1). Count that in the signed-in latency budget.
- **Auction poll (NFR-03).** 1,000 concurrent viewers polling one lot every 5 s ≈ **200 req/s** straight at the VPS, four times NFR-02's 50 req/s test load, with no CDN in front. Viewers behind one IP (school networks, carrier NAT) also hit §8.1's "general 300/min" per-IP limit at about 25 pollers. Make the lot-state endpoint cheap: an in-process memo of about 1 s, and its own rate-limit bucket. A per-client `Cache-Control: max-age` does not cut load across clients. To offload the VPS, serve the poll through a Vercel route handler with `s-maxage=1–2` (countdown skew ≤ 2 s). Add a 200 req/s load test to the S0 / #11 acceptance criteria.
- **Rate limits for SSR.** Vercel's egress IPs are a dynamic shared pool; static IPs are a separate feature ([Vercel static IPs](https://vercel.com/kb/guide/how-to-allowlist-deployment-ip-address)). Keyed on `req.ip`, all SSR would share one bucket. A blanket `API_SERVER_KEY` exemption would let uncached SSR routes, such as directory search, drive unlimited API load. Instead, SSR forwards the end user's IP (from Vercel's `x-forwarded-for`/`x-real-ip`) in a header the API trusts **only** when `API_SERVER_KEY` is valid, and the limiter keys on that IP. Build and `'use cache'` calls carry no user IP and get one separate, generous bucket. This changes §8.1.

### 5. Inbound webhooks (Razorpay, Resend)

- **Raw body.** Mount `/api/v1/webhooks/*` with `express.raw({ type: 'application/json' })` **before** the global `express.json()`, as §8.1 says.
- **Razorpay.**
  - **Verify:** `validateWebhookSignature(rawBody, X-Razorpay-Signature, secret)` takes the **raw body string** ([razorpay-node wiki](https://github.com/razorpay/razorpay-node/wiki/Home)). The SDK's own example uses `JSON.stringify(payload)`. Do not copy that: Razorpay says not to parse the body.
  - **Delivery:** a 2xx is required **within 5 s**. Delivery is at-least-once, and events may arrive out of order. Failures are retried with backoff for **24 h**; after that the webhook is **disabled** and an alert email is sent ([FAQs](https://razorpay.com/docs/webhooks/faqs), [validate and test](https://razorpay.com/docs/webhooks/validate-test)).
  - **Dedupe and modes:** deduplicate on `x-razorpay-event-id`. Live and Test modes have separate webhook URLs ([validate and test](https://razorpay.com/docs/webhooks/validate-test), [webhooks](https://razorpay.com/docs/webhooks)).
  - **IP allowlist:** Razorpay publishes webhook IPs but still recommends signature checks ([whitelists](https://razorpay.com/docs/security/whitelists)).
- **Resend (and Clerk), both via Svix.**
  - **Verify:** check `svix-id`, `svix-timestamp` and `svix-signature` over the **raw** body with `resend.webhooks.verify(...)` ([Resend verify](https://resend.com/docs/webhooks/verify-webhooks-requests)). Clerk uses `verifyWebhook` (§2). Neither needs a direct `svix` dependency.
  - **Retry schedule:** immediately, then 5 s, 5 min, 30 min, 2 h, 5 h, 10 h and 10 h, about 27.6 h in total. After 5 days of failures Svix disables the endpoint ([Resend retries](https://resend.com/docs/webhooks/retries-and-replays), [Svix retries](https://docs.svix.com/retries)).
  - **Response window:** 30 s for a 2xx.
  - **Dedupe:** `svix-id` stays the same across retries ([Svix idempotency](https://docs.svix.com/idempotency)).
  - **Clock:** timestamp tolerance is **5 min** ([svix tests](https://github.com/svix/svix-webhooks/blob/main/javascript/src/webhook.test.ts)), so keep the VPS clock NTP-synced.
- **Pattern for all providers: atomic store + enqueue.** Verify. Then, in one `prisma.$transaction`, insert into `WebhookEvent` (unique provider + event id, `ON CONFLICT DO NOTHING`) and `boss.send(…, { db: fromPrisma(tx), singletonKey: provider:eventId })`. Then return 200. pg-boss's `db` option runs the job insert inside the caller's transaction; the Prisma adapter needs Prisma v7+ with `@prisma/adapter-pg` ([pg-boss adapters](https://github.com/timgit/pg-boss/blob/master/docs/api/adapters.md)). If the insert and the enqueue were separate, an enqueue failure after the insert commits would make the provider's retry hit the conflict, receive a 200, and the event would never be processed (§3.6). If the adapter cannot be used: on conflict, re-enqueue when `processedAt IS NULL`, using the same `singletonKey`. This fits Razorpay's 5 s window. Outages shorter than the retry windows heal themselves; the §3.6 reconciliation job covers longer Razorpay gaps.

### 6. Environments, isolation and API-down behaviour

- **Before the VPS exists.** The map deploys the backend "once the build is solid", but prototypes go to Vercel previews before that. Until a non-production API exists, previews run against fixtures or a mock-API flag, or show no API data. #7 decides this ("environments before the VPS exists").
- **After the VPS: options for #7.** (a) A staging API (`api-staging.foaglobal.org`: Clerk dev, Razorpay test, Turnstile test keys) beside production on the same VPS. (b) The same staging API on a separate small VM. Either way, all previews point at it.
- **Isolation rules if staging shares the VPS** (SG-01, NFR-06, NFR-02/04). Staging is public, has a relaxed CORS pattern and shows Swagger at `/docs` (§8.1). So:
  - Staging holds seeded or synthetic data only, and is never restored from prod backups unless anonymised.
  - It gets a separate Docker network and Postgres role/database, with no access to prod volumes or secrets.
  - Staging containers get CPU and memory limits so they cannot starve production.
- **Fork PRs.** The repo is public. Git Fork Protection (on by default) makes fork PRs wait for authorisation before they get env vars or the OIDC token. Keep it on. Preview env vars hold staging-only secrets that cannot reach the prod API ([Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github), [security settings](https://vercel.com/docs/project-configuration/security-settings)).
- **When the API is down (NFR-04 covers web too).** Signed-in pages fail. Public pages survive only while cache entries are within `expire`. So:
  - Give public `cacheLife` profiles a long `expire`, so stale pages keep serving while background revalidation fails.
  - Add error boundaries with friendly fallbacks to dashboards.
  - Run uptime checks on both `/health` and a web page that calls the API.
  - Entries deleted for SG-05 re-render on the next request and error while the API is down. This fails closed, which is the intent.

## Recommendation

1. **Plan and region.** Vercel **Pro**; `vercel.json` `"regions": ["bom1"]`; VPS in Mumbai. Measure SSR→API round-trip time once the host is chosen (#7/#11).
2. **Environments (for #7 to decide).** Before the VPS: previews use fixtures or a mock API. After: one non-production API (same VPS with the §6 isolation rules, or a small separate VM) on Clerk dev + Razorpay test + Turnstile test keys, with all previews pointing at it. Keep CI and demos within the 100-user dev cap using `+clerk_test` users and Testing Tokens. Consider a Preview Deployment Suffix on an FOA-owned domain, so the origin pattern stops matching other teams' `vercel.app` URLs; check the suffix domain requirements first.
3. **API middleware order:**
   1. helmet
   2. request id (generate, or accept the SSR-forwarded `X-Request-Id`)
   3. cors (`CORS_ORIGINS` exact; plus `CORS_ORIGIN_PATTERN` outside prod; headers as §1; `maxAge: 7200`; `credentials: false`)
   4. webhooks router with `express.raw`
   5. `express.json()`
   6. `clerkMiddleware({ jwtKey })`, **no `authorizedParties`**, then the `azp` check (present and not allowed → 401; absent → accept)
   7. rate limiter: `trust proxy = 1`; key = user id when signed in, else the forwarded client IP when `API_SERVER_KEY` is valid, else `req.ip`; separate buckets for build/`'use cache'` traffic and for the lot-state poll
4. **Revalidation.**
   - Production web: `POST /api/revalidate` at `WEB_BASE_URL`. It checks `Authorization: Bearer REVALIDATE_SECRET` in constant time and validates `{ tags: string[], srcImages?: string[], mode: 'invalidate' | 'delete' }` with Zod.
   - It calls `invalidateByTag(tags)` for ordinary changes, or `dangerouslyDeleteByTag(tags)` + `dangerouslyDeleteBySrcImage(srcImages)` for SG-05. Each is one call per batch. On an error containing `429` it returns 503 so the caller retries. It returns what it purged.
   - Keep `revalidateTag` only if a preview test shows `@vercel/functions` misses `'use cache'` entries. Check the request logs for `STALE` / "Tag-based invalidation" and `REVALIDATED` / "Tag-based deletion".
   - **SG-05 paths** (consent withdrawal, unfeature, hide): the API request `await`s the purge with a short timeout. On failure it falls back to a pg-boss job with a short `retryDelay`, and alerts if the purge is not acknowledged within 5 min.
   - **Ordinary public-data changes**: a batched worker job.
   - Also set `images.minimumCacheTTL` low for `media.foaglobal.org` as a second line of defence.
   - Non-production API: Vercel REST purge endpoints with `target=preview`.
5. **Webhooks.** Verify, then store + enqueue in one transaction, then return 200 (§5), for Clerk, Razorpay and Resend, with a separate secret per environment. Use `resend.webhooks.verify` and Clerk's `verifyWebhook`, with no direct `svix` dependency.
6. **Env additions (§3.7), derived where possible.**
   - API: `CLERK_JWT_KEY`, `CLERK_PUBLISHABLE_KEY`, `API_SERVER_KEY`. Non-production only: `CORS_ORIGIN_PATTERN`, plus a Vercel purge token and project id for the REST purge.
   - Allowed `azp` values reuse `CORS_ORIGINS`, and the revalidate URL is `WEB_BASE_URL + '/api/revalidate'`. There is no `CLERK_AUTHORIZED_PARTIES` and no `WEB_REVALIDATE_URL`.
   - Web: `API_SERVER_KEY`, server-only and never `NEXT_PUBLIC_`.

## Open risks

- **`azp` behaviour can change.** Clerk may later enforce `azp` elsewhere, or start minting it consistently. Add an S0 test that signs in, lets the token expire, loads a signed-in server page, sends a browser mutation, and decodes both tokens. Re-run it on every `@clerk/*` upgrade.
- **The preview-origin pattern can be spoofed** on `vercel.app`: a Vercel team whose slug ends in `-<scope>` would match. The impact is low, because previews reach only non-production with Bearer auth and no cookies. A Preview Deployment Suffix closes the gap. Truncation of labels over 63 characters can stop long branch names from matching.
- **Purge coverage is unverified.** It is not yet confirmed that `@vercel/functions` tag purges clear `'use cache'` entries (including per-instance in-memory ones), or that a `target=preview` purge clears every preview deployment. Test both on a preview in S0.
- **Purge rate limit.** 200 calls/s per team on Pro. Batching tags into one call keeps this far away, and `@vercel/functions` turns a 429 into a retry instead of a silent drop.
- **Clerk dev-instance quota** (100 users, 100 emails and 20 SMS a month) is shared by local development, CI and previews unless previews get their own Clerk application.
- **One VPS is a single point of failure.** Webhook retries cover about 24 h (Razorpay) and about 27.6 h (Svix); after that Razorpay disables the webhook and needs re-enabling by hand. Public pages serve stale only within `expire`. If staging shares the box, its limits must stop it starving production.
- **Unmeasured latency.** VPS ↔ `bom1` round-trip time and the iOS preflight cost are not measured yet.
- **Map is out of sync.** §3.1 and §3.7 still say Railway and Neon, which the map has ruled out. The SPEC deltas table splits the edits between #7's and #10's `docs:` PRs.
